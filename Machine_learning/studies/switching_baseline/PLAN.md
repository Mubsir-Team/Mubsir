# Switching-baseline study — revised analysis plan (for review; NOT yet pre-registered)

**Status:** draft for the owner's review, 2026-11-26.
- Nothing has been trained.
- No attack data will be generated, simulated, injected or modified.
- No frozen dataset or model will be changed.
- It replaces AUDIT.md §6–§7 (owner decision: no new attack scenarios).
- Population counts below come from `population_check.py` (read-only), output `results/population_check.json`.

## 1. Objective
Does measuring channel switching **relative to an employee's own historical (2010) switching rate** add useful detection
information beyond the existing 100 MUBSIR features?

Two sub-questions must be separated:
- **(a)** Does switching-rate information add anything at all?
- **(b)** Does the **personal** reference (the employee's own 2010 rate) add anything beyond the same quantity measured
  against a **population** reference?

## 2. Constraints, as instructed
1. **Habit** comes only from existing 2010 activity (the fixed baseline period).
2. **Attack data:** only the existing Dev simulation (real NB10 attacks) and the cases already generated by
   `study_controlled_rotation/`, read-only. No new scenarios, schedules or injected events.
3. **Population:** Dev users only. The test set, test users' rows and test scores are never read.
4. **Habit measure:** switching **rate**, not switch counts (shortcut risk, AUDIT §4).
5. **Integrity:** no training until this plan is reviewed and frozen as `PREREGISTRATION.md` with a SHA-256 hash.

## 4. Populations

- The 2010 habit rate among eligible users has tertile cuts 0.387 and 0.500 (10th–90th percentile 0.22–0.61).

## 5. Features (causal; day t uses days ≤ t only)
Definitions:
- **Deviation day:** Σ_c E_c > 0.
- **Dominant channel:** argmax_c E_c.
- **Linked pair:** at most 2 quiet workdays between two deviation days.
- **Change:** a linked pair whose dominant channel differs.

These are the same definitions used in the closed study.

For a window w ∈ {10, 20} ending at day t: `pairs_w` = linked pairs, `changes_w` = changes, `rate_w` = changes_w / pairs_w.

Reference rates (neither ever enters a model directly):
- **r₀ (personal):** the user's 2010 rate = changes / linked pairs over all 2010 baseline workdays.
- **m₀ (population):** the median of r₀ over the 714 eligible users, a single constant that does not depend on labels.

| Arm | Features | Count |
|---|---|---:|
| **A** | the 100 MUBSIR features, refit on the 714 users | 100 |
| **R** (population reference) | A + `rate_dev_pop_w = rate_w − m₀` (0 if pairs_w = 0) + `excess_pop_w = changes_w − m₀·pairs_w`, for w = 10, 20 | 104 |
| **H** (personal habit) | A + `rate_dev_hab_w = rate_w − r₀` (0 if pairs_w = 0) + `excess_hab_w = changes_w − r₀·pairs_w`, for w = 10, 20 | 104 |

R and H carry the same switching information and differ **only** in the reference rate (population vs personal). So H − R
isolates the value of the personal baseline, and H − A measures the total added value.

## 6. Training and evaluation (no new data)
**Training**
- LightGBM defaults, label `y_10`.
- The existing 5×3 folds restricted to the 714 users, with roles, seeds (42 + repeat) and early stopping as in Stage A.

**Evaluation in P1**
- Each user is scored only by fold models for which they are in validation.
- Thresholds are cross-fitted from the whole-period peak scores of the eligible benign users in the other folds: iso-FPR 3%
  primary, 1% secondary.
- An attacker is detected if any day with `y_10 = 1` scores above the threshold.

**Evaluation in P2**
- Each case is scored by the P1 fold model that has its host in validation.
- Detection uses the span [first attack day, last attack day + 9], as in the closed study.

**Uncertainty**
- 2,000 bootstrap resamples.
- Resampling unit: users (P1) or hosts (P2), stratified by attacker vs benign.
- Estimands are averaged over the 3 repeats inside each resample; percentile 95% CIs.

## 7. Estimands
**Primary (P1, iso-FPR 3%):** Δ₁ = Det(H) − Det(A) over the 347 eligible attackers.

**Key secondary:** Δ₂ = Det(H) − Det(R), the value of the personal reference itself.

**Secondary (Holm across all of them):**

| ID | Estimand |
|---|---|
| S1 | Δ₁ at iso-FPR 1% |
| S2 | Δ₂ at iso-FPR 3% |
| S3 | habit moderation: Δ₂ among attackers in the low-habit tertile minus Δ₂ in the high-habit tertile (tertiles of r₀) |
| S4 | attack switching level: Δ₁ for High-switching attackers minus Δ₁ for Low-switching attackers |
| S5 | P2 matched order: [H − A](ROT) − [H − A](BLK), 123 H146 hosts |
| S6 | P2: [H − R](ROT) − [H − R](BLK) |
| S7 | row-level PR-AUC difference H − A (pooled OOF) |

**Descriptive only:**
- the P2 habit-tertile split (about 41 hosts per tertile, underpowered);
- latency;
- results by channel count and stealth level;
- unique detections;
- R − A.

## 8. Gates (run after pre-registration, before any estimand)
1. **Unit check.** The four features give the expected values on toy sequences, and r₀ reproduces `results/habit_2010_dev_users.csv`.
2. **Shortcut gate.** For each R and H feature, compute the user-level mean over rows before the first attack day
   (attackers) or over all rows (benign). The attacker-vs-benign AUC, folded, must be < 0.60. If an H feature fails, the
   primary is reported as inconclusive; features are not dropped, because H is the object of study.
3. **Fold integrity.** Every restricted fold keeps ≥ 20 benign validation users and the original grouping.

## 9. Decision rules (proposed; frozen at pre-registration)
| Outcome | Condition |
|---|---|
| **1 — personal switching habit adds information** | Δ₁ ≥ +2 points with CI > 0, **and** Δ₂ > 0 with CI > 0 |
| **2 — switching rate helps, the personal reference does not** | Δ₁ CI > 0, Δ₂ CI includes 0 |
| **3 — no added value** | Δ₁ and Δ₂ CIs both within (−3, +3) points |
| **4 — inconclusive** | a gate fails, or none of the above (for example CIs too wide) |

**Power:** with 347 paired attackers, a difference of about 2–3 points should be resolvable. The tertile and P2 analyses can
resolve only large effects.

**Adoption:** no result changes the frozen MUBSIR. At most, an Outcome 1 justifies validation on new data.
