# Switching-baseline study — pre-registration (frozen protocol)

**Written:** 2026-11-26, after the Phase 0 audit (`AUDIT.md`), the read-only population check (`population_check.py`) and
the owner's approval of `PLAN.md` with its recommended choices. **Before** any feature computation on 2011 rows, any
training, or any estimand.

This file is hashed. The hash is stored in `PREREGISTRATION.sha256` and checked by every later script. Any later change must
be a dated amendment with a new hash.

**No rule below may be changed after results are seen. A null or inconclusive result is a valid outcome.**

## 1. Objective and hypotheses
**Objective:** does measuring channel switching relative to an employee's own historical (2010) switching **rate** add
useful detection information beyond the existing 100 MUBSIR features?

- **H1 (primary):** adding habit-relative switching features (arm H) improves user-level detection of the existing Dev
  attacks, compared with the 100 features alone (arm A), at matched false-positive rate.
- **H2 (key secondary):** the improvement comes from the **personal** reference: arm H beats arm R, which holds the same
  switching quantities measured against a population reference.

## 2. Constraints (owner's instructions)
1. **No attack data is generated, simulated, injected or modified.** No new scenario, schedule or event.
2. **Data used:**
   - 2010 historical activity, for the habit;
   - existing 2011 Dev rows, with their existing attacks and pre-attack activity;
   - the cases already generated by `study_controlled_rotation/`, read-only.
3. **Population:** Dev users only. Test users' rows, test scores and test decisions are never read.
4. **Habit measure:** a switching **rate**, never raw switch counts.
5. **Frozen artefacts:** no frozen model, manifest, calibration, threshold, allowlist, dataset, split, label, OOF or
   report is modified.
6. **Integrity:** SHA-256 of all pre-existing `Model/` files (closed studies included) is taken before
   (`hashes_before.json`) and after. All outputs go inside `study_switching_baseline/`. `EXPERIMENT_LOG.md` records every
   command and seed.

## 4. Definitions
**Daily deviation**
- E_c(t) = max(0, x_c(t) − P50_c) / max(1, P95_c − P50_c).
- P50/P95 are the fixed 2010 baselines: linear quantiles over active 2010 workdays (weekday and logon > 0).
- Channels without a baseline have E_c = 0 (the `E_*_today` contract rule).

**Switching terms**
- **Deviation day:** Σ_c E_c > 0.
- **Dominant channel:** argmax_c E_c, with ties broken Email < USB < HTTP.
- **Linked pair:** consecutive deviation days with at most 2 quiet workdays between them.
- **Change:** a linked pair whose dominant channels differ.

**References (neither ever enters a model as a feature)**
- **Personal habit r₀** = changes / linked pairs over all of the user's 2010 baseline workdays.
- **Habit eligibility:** ≥ 2 channels with a baseline and ≥ 20 linked pairs in 2010.
- **Population reference m₀ = 0.4444444444** = the median r₀ of the 714 eligible dev users. It is label-free and frozen
  here.

## 5. Populations
**P1 (primary).** The 714 habit-eligible dev users: 347 attackers and 367 benign.
- All arms are trained and evaluated on exactly these users.
- **Why:** 144 of the 511 benign users but only 1 of the 348 attackers are ineligible, so a missing habit would be a label
  shortcut.

**P2 (secondary).** Existing H146 cases of the 123 habit-eligible hosts:
- ROT and BLK, L ∈ {6, 12}: 246 cases per variant;
- FIX and SIM: descriptive only.

**Habit tertiles.** Cuts are fixed from the 714 eligible users: low r₀ ≤ 0.3868524, mid, high r₀ > 0.5. Eligible attackers
per tertile: low 91, mid 124, high 132.

## 6. Features (causal: day t uses rows ≤ t of the same user or case)
For w ∈ {10, 20}, over rows [t − w + 1, t] (a partial window at the start of the series):
- `pairs_w` = number of linked pairs with both days in the window;
- `changes_w` = number of changes;
- `rate_w` = changes_w / pairs_w.

| Arm | Added features | Count |
|---|---|---:|
| **A** | none: the 100 MUBSIR features (manifest order), refit on P1 | 100 |
| **R** (population reference) | `rate_dev_pop_w` = rate_w − m₀ if pairs_w > 0, else 0; `excess_pop_w` = changes_w − m₀ · pairs_w | 104 |
| **H** (personal habit) | `rate_dev_hab_w` = rate_w − r₀ if pairs_w > 0, else 0; `excess_hab_w` = changes_w − r₀ · pairs_w | 104 |

For P1 the features come from the dev rows' `E_*_today`. For P2 they come from the cases' `E_*_today`, using the host's r₀.

## 7. Gates (after this freeze, before any estimand)
- **G1 — unit check.** On toy E sequences of six consecutive deviation days with r₀ = 0.4:
  - E U H E U H gives pairs_10 = 5, changes_10 = 5, rate_dev_hab_10 = 0.6, excess_hab_10 = 3;
  - E E U U H H gives 5, 2, 0.0, 0.0;
  - an all-quiet window gives 0 for every feature;
  - r₀ recomputed by the feature code equals `results/habit_2010_dev_users.csv` (|diff| ≤ 1e-12) for all 714 users.
- **G2 — shortcut gate.**
  - For each of the 8 R and H features, take the per-user mean over rows before the first `y = 1` row (attackers) or over
    all rows (benign).
  - Compute the attacker-vs-benign AUC on P1, folded to ≥ 0.5.
  - If **any H feature** has AUC ≥ 0.60, the study's outcome is **4 (inconclusive)**. The analysis is still run and
    reported descriptively, and features are not dropped.
  - R features are reported. If an R feature fails, H2 is reported as inconclusive.
- **G3 — fold integrity.** In every repeat and fold, the restricted validation fold keeps ≥ 20 benign and ≥ 20 attacker
  users. Fit, early-stopping and validation groups do not overlap. Otherwise the study stops (outcome 4).
- **G4 — pipeline check.** Arm A on P1 is trained with exactly the Stage A procedure, with `05_tune.load()` and
  `models.fit_predict`, unmodified. A failure of any gate is logged before anything else is computed.

## 8. Training and scoring
- **Model:** LightGBM defaults through `models.fit_predict("lightgbm", ...)`, label `y_10`.
- **Folds:** the existing `cv_folds.csv` folds (5 × 3, seeds 42 + repeat), with every role restricted to P1 users.
  Early stopping on the restricted es users.
- **P1 scoring:** each P1 user's rows are scored by the fold model of each repeat for which the user is in validation (OOF).
- **P2 scoring:** each P2 case is scored, in each repeat, by the fold model whose validation fold contains its host. Case
  rows never enter training.

## 9. Evaluation
**Thresholds (cross-fitted)**
- For arm a, repeat r and fold k: `threshold_at_fpr(peaks, f)` from `pipeline/metrics.py`.
- The peaks are the whole-period peak OOF scores of the P1 benign users **not** in fold k.
- **f = 0.03 primary, 0.01 secondary.**

**Detection**
- **P1 attacker:** at least one row with `y_10 = 1` scores above the threshold of its validation fold.
- **P2 case:** at least one row in [first attack day, last attack day + 9] scores above the threshold of its host's fold.

**Aggregation and uncertainty**
- Det = share of attackers (P1) or cases (P2) detected, averaged over the 3 repeats.
- **Bootstrap:** 2,000 resamples, `numpy.random.default_rng(2026)`.
- **Resampling unit:** users (P1) or hosts (P2), stratified by attacker vs benign. In P2 all of a host's cases are resampled
  together.
- Estimands are recomputed in each resample; percentile 95% CI.
- Two-sided p = min(1, 2 · min(share ≤ 0, share ≥ 0)).

## 10. Estimands
**Primary (P1, iso-FPR 3%):** Δ₁ = Det(H) − Det(A), over the 347 attackers.

**Key secondary:** Δ₂ = Det(H) − Det(R) at iso-FPR 3%.

**Secondary tests (Holm–Bonferroni across S1–S7, α = 0.05):**

| ID | Estimand |
|---|---|
| S1 | Δ₁ at iso-FPR 1% |
| S2 | Δ₂ at iso-FPR 3% (= the key secondary) |
| S3 | Δ₂ among low-habit-tertile attackers minus Δ₂ among high-habit-tertile attackers |
| S4 | Δ₁ among High-switching attackers minus Δ₁ among Low-switching attackers (`switching_level`) |
| S5 | P2: [Det(H) − Det(A)](ROT) − [Det(H) − Det(A)](BLK), pooled over L |
| S6 | P2: [Det(H) − Det(R)](ROT) − [Det(H) − Det(R)](BLK), pooled over L |
| S7 | row-level PR-AUC(H) − PR-AUC(A) on pooled P1 OOF rows (mean over repeats), user bootstrap |

For S3 and S4, the thresholds are the common thresholds above; the subgroups split the attackers only.

**Descriptive only (no tests):**
- R − A;
- P2 by habit tertile, FIX and SIM;
- latency (workdays from the first `y = 1` row to the first detection);
- results by channel count, stealth level and switching level;
- unique detections (attackers detected by H but not A in ≥ 2 of 3 repeats, and the reverse);
- realised held-out benign FPR of every threshold.

## 11. Decision rules (applied in this order)
| Outcome | Condition |
|---|---|
| **4 — inconclusive (gate)** | G2 (H features) or G3 fails |
| **1 — personal switching habit adds information** | Δ₁ ≥ +0.02 with CI entirely > 0, **and** Δ₂ > 0 with CI entirely > 0 |
| **2 — switching rate helps, the personal reference does not** | Δ₁ CI entirely > 0, **and** Δ₂ CI includes 0 |
| **3 — no meaningful added value** | the CIs of Δ₁ and Δ₂ both lie within (−0.03, +0.03) |
| **4 — inconclusive** | none of the above |

- **Power note:** 347 paired attackers should resolve differences of about 2–3 points. S3–S6 resolve only large effects,
  and their nulls are reported as "no large effect".
- **Adoption:** no result modifies the frozen MUBSIR. At most, Outcome 1 justifies validation on new data, under a new
  protocol.
